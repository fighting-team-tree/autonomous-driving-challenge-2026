# EXP-E001 — E2E를 우리 자원으로 완주할 수 있는가

## 배경

E2E는 세 트랙 중 **자원 격차가 가장 큽니다.**

| | |
|---|---|
| 주최측 학습 환경 | **GPU 8장 서버로 약 1주일** |
| 우리 자원 | RTX 3060 / 5060, Colab, Runpod |

리더보드 마감(9/23)까지 6주입니다. 3트랙 균등 병렬로 등록했지만, E2E에 몇 주를 쓰고
"결국 학습이 안 끝났다"로 끝나는 것이 최악의 시나리오입니다. 그 시간을
[궤적예측](../../competition/prediction.md)에 썼다면 점수가 나왔을 테니까요.

그래서 이 실험은 **성능 실험이 아니라 판정 실험**입니다. 목적은 점수를 올리는 게 아니라
**[O-001 트랙 우선순위 재조정](../../decisions.md#o-001)에 넣을 숫자를 만드는 것**입니다.

빨리 측정할수록 좋습니다. 이 판정이 늦어질수록 잘못된 트랙에 쓰는 시간이 늘어납니다.

## 가설

소규모(예: 학습 시나리오 10~20개, 1 epoch)로 시간을 재고 전체 규모(376 시나리오)로
외삽하면, 우리 자원에서의 총 학습 시간을 **오차 범위 안에서 추정할 수 있다.**

그리고 그 추정치는 다음 중 하나로 떨어집니다:

- **3일 이내** → E2E를 정상 트랙으로 진행
- **3일 ~ 2주** → 축소 학습(부분 데이터, 짧은 스케줄)으로 제출은 하되 비중을 낮춤
- **2주 초과** → E2E는 베이스라인 제출까지만 하고 자원을 다른 트랙으로 이동

## 실험 설계

- **바꾼 것**: 학습 규모만 축소. 모델·하이퍼파라미터는 배포 기본값
- **고정한 것**: 제공 도커 이미지(`etri-vad_cu128.tar`, CUDA 12.8), VAD-tiny 기본 설정
- **비교 대상**: 주최측 공표치(GPU 8장 × 1주일)
- **판정 기준**: 위 세 구간 중 어디에 들어가는가

### 절차

```bash
# 1) 도커 이미지 로드 — E2E는 CUDA 12.8이라 Planning(CUDA 13)보다 드라이버 요구가 낮다
docker load -i etri-vad_cu128.tar

# 2) 학습 데이터 일부만 받아서 변환 (train 376개 중 10~20개)
# 3) 1 epoch 학습 시간 측정
# 4) 전체 규모로 외삽
```

전체 데이터(250~500GB)를 다 받기 전에 시작하세요. **10~20개 시나리오면 충분합니다.**

### 반드시 측정할 것

| 측정 | 왜 필요한가 |
|---|---|
| 시나리오당 학습 시간 | 376개로 외삽하는 근거 |
| **VRAM 사용량과 최대 batch size** | 3060 12GB에서 기본 설정이 도는가 |
| 도커 이미지가 우리 드라이버에서 뜨는가 | CUDA 12.8 요구 충족 여부 |
| 데이터 변환(전처리) 시간 | 학습 시간에 가려지기 쉬운 비용 |
| 추론 시간 (단일 scene) | 100ms 페널티 기준선 대비 |
| Colab/Runpod 시간당 비용 | 완주 비용 추정 |

VRAM이 특히 중요합니다. batch size를 크게 줄여야 하면 학습 시간이 선형보다 나쁘게
늘어나므로 외삽이 낙관적으로 빗나갑니다.

!!! tip "베이스라인 제출은 별개로 확보하세요"
    학습이 어렵다고 판단되더라도, **제공된 VAD-tiny 가중치로 추론만 돌려서 제출**하면
    리더보드 점수는 남습니다. 수상 후보가 아니더라도 참가 실적과 발표 자료가 됩니다.
    판정이 "2주 초과"로 나오면 이쪽으로 전환하세요.

!!! warning "여기에 seed·하이퍼파라미터를 적지 마세요"
    이 저장소는 public입니다. 복붙하면 바로 돌아가는 값은 MLflow에만 남깁니다.
